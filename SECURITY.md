# Безопасность

Сервис имеет доступ к Telegram Bot API токену и принимает трафик Bridge. Это доверенный локальный компонент с существенными полномочиями. Он слушает только IPv4 loopback; не публикуйте его порт через внешний reverse proxy. Ограничьте доступ к машине и приватному каталогу данных.

## Граница текущей версии

По умолчанию панели читают разрешённые поля реестра установленных плагинов. При `bitrixReadOnly: true` сервис также читает scoped env Bitrix24: webhook и маркер исходных настроек. Они передаются отдельному дочернему процессу установленного плагина для чтения настроек и проверки подключения/прав. Это расширение доверия: процесс iva-panels технически получает секрет с полномочиями webhook. Он не читает vault, содержимое задач или файлы доставки и не выполняет бизнес-записи задач/файлов. При отдельном opt-in редактор меняет локальную политику плагина.

Для собственного входящего события проверяются общий секрет Bridge, разрешённый пользователь, личный чат и отсутствие признака бота. Кнопка дополнительно связана с владельцем, чатом, сообщением, ревизией и сроком экрана. Текст преобразованного события не является независимым доказательством ручного нажатия: обладатель общего секрета может его подделать. Эти проверки недостаточны для разрешения чувствительных операций записи.

Остальные запросы передаются исходному Eve по фиксированному loopback origin, включая заголовки аутентификации. Перехват всей цепочки означает, что отказ сервиса может нарушить работу Bridge. До подключения нужен проверенный возврат к исходному маршруту.

## Хранение и ошибки

`config.json` требует права 0600; секрет и Bot API токен задаются явно оператором. Они не попадают в журналы. `screens.json` содержит идентификаторы владельца, чата, сообщения, представления, сроки и хеши событий; он записывается атомарно с правами 0600. Это приватные пользовательские данные. Полные входящие сообщения не сохраняются. Каталог данных должен принадлежать выделенному пользователю и иметь права 0700.

Повреждённое состояние останавливает запуск. Не удаляйте его автоматически: это может сбросить защиту от повторов. Нет миграции формата или автоматического удаления данных после деинсталляции. Оператор управляет резервами и удалением.

Неоднозначная первоначальная отправка не повторяется. Редактирование повторяет только сохранённое представление. Если сообщение удалено или Bot API постоянно отказывает, доставка может остаться незавершённой и блокировать этот экран; открытие новой панели и диагностика предпочтительнее ручной правки состояния.

## Сообщение об уязвимости

До открытия репозитория сообщайте владельцу через согласованный приватный канал. Не отправляйте токены, идентификаторы чатов или реальные данные в GitHub issues. Перед публичным открытием владелец должен включить приватные сообщения об уязвимостях и проверить этот процесс.

## Адаптер Bitrix24

Дочерний процесс получает только `BITRIX24_WEBHOOK_BASE_URL`, `BITRIX24_SETTINGS_DEFAULTS`, `PLUGIN_ROOT` и `PLUGIN_DATA`. Общий env Ивы, Bot API token и другие параметры не наследуются. stderr отбрасывается. В адаптере фиксированы три tool: `bitrix24_settings` только с `screen: actions/privacy`, `bitrix24_connection_check` и `bitrix24_capabilities` с пустыми аргументами. Без редактора replies не вызываются. При `bitrixSettings: true` к `bitrix24_settings` допускаются только ревизионный выбор из фиксированного списка и confirm/cancel token, полученный из ответа preview. Screen events и бизнес-инструменты не вызываются.

SDK ограничивает stdio buffer 256 KiB, общий сигнал ожидания — 15 секунд; клиент закрывается и завершает дочерний процесс после страницы или ошибки. Ответ проверяется схемой и проектируется на известные поля; markdown, имена сотрудников, неизвестные scopes и сырые ошибки не выводятся и не сохраняются. Проверка соединения получает профиль webhook-пользователя внутри процесса Bitrix; персональные поля не попадают в панель. Enabled/trusted проверяются перед каждым разделом. Это проверка реестра перед запуском, а не транзакционная блокировка обновления/выключения плагина.

Адаптер не подключается к общей HTTP MCP-сессии Eve и не использует её bearer token. Собственная stdio-сессия не мешает текущим вызовам Eve, но добавляет короткий процесс и сетевые запросы при проверке подключения/прав.

## Редактор настроек

Выбор берётся из сохранённой кнопки, привязанной к owner/chat/message/revision/TTL; собственный секрет Bridge обязателен. Это прежняя граница доверенного Bridge, а не независимая криптографическая проверка raw Telegram tap. Клиент не получает API tool для произвольного reply. Preview проверяется схемой: текущая ревизия, UUID, согласованные confirm/cancel и срок. Токены сохраняются только в приватном view, callback несёт индекс кнопки.

Bitrix24 проверяет собственные offer token, identity, revision, TTL и общий policy lock. Confirm меняет только локальные настройки и отменяет прежний task draft; он не меняет webhook permissions и не выполняет действия на портале. Поля people/email согласует сам Bitrix. Одно глобальное предложение может быть заменено другим экраном или прежним разговорным меню: устаревшее подтверждение отвергается. Закрытие или новая команда не отменяют предложение автоматически; оно истекает, а отмена выполняется отдельной кнопкой.

До prepare/confirm/cancel сохраняется квитанция `acting`. После ошибки обновления Telegram повторяется только сохранённый вид. Неизвестный исход или crash между эффектом и сохранением вида не повторяет mutation: при повторе того же события панель читает настройки и сообщает о неопределённом результате. Acting квитанции удерживаются до повторной доставки события и защищают экран от другого действия/очистки; универсального автоматического восстановления нет. При убийстве Bitrix-процесса во время policy lock может остаться его штатный stale lock; его не удаляют автоматически, требуется диагностика оператора.

## Панель отправки файлов

Карточка читает только manifest установленного `file-delivery` (до 8 КиБ) и разрешённые поля регистрации. Контент файлов, vault, Bot API env другого плагина и update-offer не читаются. Перед каждой страницей проверяются enabled/trusted. Для неизвестной версии правила 0.3.2 не объявляются подтверждёнными.

Только кнопка «Проверить stable» делает GET на фиксированный публичный `mamysh/iva-file-delivery`: GitHub API commit/CI и raw manifest на validated SHA. Общий deadline 15 секунд, streamed limit 128 КиБ для API и 8 КиБ для manifest, redirects запрещены; credentials и произвольные URLs не принимаются. Ответы проходят схему, сырые ошибки и поля не выводятся. Последний push run `ci.yml` на candidate SHA определяет CI; отсутствие run не означает success. Read-only запрос может быть повторён после crash до сохранения view, установка и offer не вызываются. GitHub видит обычные сетевые метаданные сервера. Проверка сравнивает stable, а не меняет закреплённый источник установки.

## Автообнаружение и descriptor v1

Реестр ограничен 5 МиБ/1000 записей; имена валидируются как имена Ивы (lowercase letters/digits/hyphen/period, максимум64, без --/..), дубли отвергаются. Все регистрации видны, включая недоверенные и выключенные. Чтение manifest до8КиБ и описание до500символов не исполняет код. Source/paths/env/прочие поля не выводятся. SHA показывается только в допустимом формате. Статус не является проверкой фактической службы.

Descriptor читается только для enabled/trusted из фиксированного panels.json до32КиБ. Ограниченное чтение из file descriptor с O_NOFOLLOW/O_NONBLOCK проверяет обычный файл и размер, включая рост после stat; последний компонент не может быть symlink. Это не защита от владельца машины или подмены родительского каталога. Имя/версия сверяются с manifest, pages/targets/unknown fields/итоговый escaping проверяются.

Внешний descriptor может только показать literal text и перейти в собственную страницу. Его targets оборачиваются в namespace; он не может вызвать Bitrix mutation, close/global action, shell/MCP/URL или читать env/config/vault. Общий динамический протокол не реализован. Ошибка descriptor оставляет базовую карточку, malformed registry останавливает обработку. Сохранённые callback IDs не содержат путей, secret или содержимого descriptor. Тексты разделов сохраняются в приватном screen view, поэтому автор не должен помещать туда секреты.
