# Вопросы и решение проблем

## Почему плагин виден, а настроек нет?

Каталог читает все регистрации. Для настроек нужны включение, доверие,
`panels.json` v2, работающая служба API и `dynamicPanels: true` в конфиге Panels.
Карточка отличает объявленный API от фактической доступности при открытии.
V1 предоставляет только справку. [Как подключить плагин](INTEGRATION.md).

## Можно подключить любой сторонний плагин?

При доступных исходниках можно добавить общий контракт, не меняя код Panels.
Для закрытого плагина нужны подходящий API или доработка автора.
Кнопка «Как добавить настройки» помогает подготовить запрос Иве; она не патчит
установленные плагины автоматически и не выдаёт доверие.

## Нужен ещё один Telegram-бот?

Нет. Panels использует бота Ивы и единственный штатный Bridge.
Свой getUpdates не запускается. Нужна операторская настройка локального маршрута.

## Обычные ответы Ивы пропали после подключения

Сначала верните адрес назначения Bridge прямо на исходный Eve и проверьте health
и обычный ответ. Проверьте назначенный порт Panels, config 0600 и loopback upstream:
он не должен указывать на сам Panels. Active процесса недостаточно, дождитесь listener.
[Установка и возврат маршрута](SETUP.md).

## Кнопка устарела или сообщение удалено

Откройте новый `/panels`. Экраны ограничены сроком и revision, а чужая или старая
кнопка не выполняет новое действие. При pending/неизвестном исходе сначала
проверьте результат операции. Новый экран не разрешает повторить внешний эффект.

## Карточка не пришла, но запрос завершился ошибкой

Потерянный ответ Telegram может означать, что сообщение уже отправлено.
Не создавайте новый requestId и не повторяйте действие автоматически.
Используйте тот же запрос и собственную проверку результата плагина.
`delivery_unknown` — неизвестная доставка, не отказ бизнес-операции.
[Контракт карточек](CHAT_CARDS.md).

## Почему больше не создаются карточки?

В store до 100 экранов. После истечения их срока обычный `/panels` очищает
экраны без защищённых acting/editing событий. Если остались незавершённые действия,
нужна диагностика их результата. Не удаляйте `screens.json` или журналы ради повтора.

## Почему enable/disable может отказать на 0.5.7?

Поддержка добавлена в **0.3.0-rc.4** для exact commit **ae313753a1ae**.
Предыдущие rc.2/rc.3 знают только менеджеры 0.4.12/0.4.14.
Проверьте фактически установленную версию Panels, текущую сборку Ивы и
настройку `lifecycle`. Совпадения номера 0.5.7 недостаточно: адаптер проверяет
исходники менеджера и привязку CLI к `current` до команды.

Ива имеет штатные enable/disable; отказ этой проверки происходит в Panels.
Не обходите его подменой хешей. [Совместимость](COMPATIBILITY.md).

## Выключил file-delivery, а Ива всё равно отправляет файлы

В ядре есть независимый `send_file`. Выключение одного плагина не является
общим запретом отправки вложений. После confirm также нужно дождаться
завершения сборки, а не ориентироваться только на раннее изменение флага реестра.

## Как безопасно передать диагностику?

Укажите версии Ивы/плагина, режим, шаги, ожидаемое и фактическое поведение.
Используйте синтетические данные. Удалите токены, webhook, идентификаторы чатов,
содержимое карточек и приватные пути. Не прикладывайте config или state целиком.
[Поддержка](../SUPPORT.md), [сообщить об уязвимости](../SECURITY.md).

## Надо подключать сам iva-panels к Panels?

Нет. Он уже обслуживает интерфейс. Его карточка показывает состояние оболочки.
Для запроса «подключить API» назовите **другой плагин**. Создавать второй API
и отдельную службу у iva-panels не требуется.

## Где мои задачи и куда идти подтверждать?

«В задачи» в сообщении Ивы сохраняет пункт в её обычный список. Это не отправка
сообщения и не подтверждение действия. Попросите Иву показать задачи в чате.
Поддерживающий chat-v1 плагин показывает предложение прямо в разговоре;
искать его в каталоге не требуется. В `/panels` открывайте настройки плагинов.

## Как Иве проверить подключение без разработки вслепую?

Загрузите `iva-panels-integration`. В установленном пакете есть `inspect.mjs`,
Node.js24 достаточно, npm и доступ к приватному Git не нужны. Он различает
отсутствующий descriptor, несовпадение версии, выключенный доступ и отказ службы;
готовность проверяет только операцией read. Это не проверка записи.
[Порядок диагностики](INTEGRATION.md#диагностика-на-установленной-иве).
