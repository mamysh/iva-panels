# Исследовательский запуск

Это инструкция для изолированной проверки разработчиком. Отдельный разрешённый владельцем боевой эксперимент с установкой и сменой маршрута Bridge описан в [COMPATIBILITY.md](COMPATIBILITY.md); он не заменяет проверки вашей установки.

## Предварительные условия

Node.js 24, Linux, `bash` и `flock`. Manifest описывает service plugin; `server.mjs` включает runtime зависимости. Для запуска сервису нужны `PLUGIN_ROOT`, `PLUGIN_DATA`, `IVA_DATA_DIR`, `IVA_SERVICE_PORT`, которые менеджер служб Ивы задаёт при установке. При отдельном тесте оператор задаёт их явно; адрес данных и порт берутся из изолированного окружения.

Создайте отдельный приватный каталог `PLUGIN_DATA` с правами 0700. Создайте в нём `config.json` с правами 0600:

```json
{
  "upstream": "http://127.0.0.1:9000",
  "secret": "REPLACE_WITH_BRIDGE_SECRET",
  "botToken": "123:REPLACE_WITH_TEST_BOT_TOKEN",
  "owners": [123],
  "mode": "passthrough"
}
```

Это placeholders. `upstream` должен быть исходным HTTP origin Eve, а порт сервиса должен отличаться. Реальные секреты передаются только через приватный файл. Даже режим passthrough сейчас требует полный config и доступное корректное состояние. Режим по умолчанию — passthrough; `/panels` в нём передаётся Иве.

Запускайте из каталога сервиса:

```sh
bash launch.sh
```

Проверка `GET /health` на loopback порту службы возвращает режим и факт работы HTTP listener. Она не проверяет Telegram, Eve, очередь или доступность внешних интеграций. Панели читают `custom/plugins.json` внутри `IVA_DATA_DIR`.

## Перед экспериментальным подключением Bridge

Проверьте exact SHA ядра и поведение Bridge по [COMPATIBILITY](COMPATIBILITY.md). Сохраните прежнюю конфигурацию маршрута и способ её восстановления. В отдельном тестовом окружении сначала проверьте passthrough, затем явно включите `mode: panels`. Только адрес назначения Bridge (`ASSISTANT_HOST` в исследованной версии) направляется на loopback порт iva-panels; origin настоящего Eve остаётся прежним и указан в config.

Порт 8735 в descriptor является запрашиваемым; используйте реально назначенный `IVA_SERVICE_PORT`, а не предполагайте свободный фиксированный порт. Никогда не направляйте upstream на сам сервис. При возврате Bridge на исходный адрес сначала проверьте прямую связь с Eve, затем остановите iva-panels. Никакое изменение маршрута не выполняется автоматически плагином.

Обязательный smoke: обычный текст, native menu, reset/cancel, открытие `/panels`, переходы в одном сообщении, дубликат и stale button, restart, очередь при занятом агенте, удалённое сообщение, отказ Telegram и возврат исходного маршрута. Изолированный маршрут модулей Bridge и собранного сервиса проверяется автоматически. В боевом эксперименте подтверждены обычный ответ Ивы, ручная навигация, restart и возврат исходного маршрута. Busy queue, отказы Telegram, native menu и reset/cancel остаются автоматическими проверками; полную матрицу живых сценариев ещё предстоит пройти.

## Диагностика

Ошибка запуска сообщает только общий код ситуации: проверьте переменные среды, права config, loopback upstream, разные порты и валидность state. Секреты и URL Bot API в журналы не выводятся. Не обходите ошибку состояния автоматическим удалением `screens.json`; сохраните приватную копию и исследуйте причину. Неоднозначную отправку заменяют новым `/panels`, а не повторной доставкой того же события.

## Штатная установка службы в Iva 0.4.12

После подготовки приватной конфигурации и явного разрешения владельца экспериментальная служба ставится штатным путём предложения плагина:

```sh
iva plugin propose /path/to/iva-panels/plugin
```

Владелец получает в своём Telegram-чате Ивы сообщение «Плагин iva-panels просит установку» и нажимает «Установить». После этого Bridge ставит точную копию предложения с проверкой digest. Прямой неинтерактивный `plugin add --trust` для `sh.iva/` штатный установщик отклоняет; подтверждение не подменяют искусственным callback или редактированием реестра.

Служба должна сначала ответить на HTTP probe, а не только показать active в systemd. Дождитесь listener и подтвердите проход health-запроса до исходного Eve, прежде чем менять маршрут Bridge. Для временного маршрута используйте отдельный override только службы Bridge; общий environment Eve остаётся прежним. Сохраните baseline, подготовьте route-only rollback и не восстанавливайте живые queue/offset/policy целиком из резервного снимка. Обратное подключение тоже ждёт готового listener.

Результаты первого разрешённого боевого эксперимента и оставшиеся проверки — в COMPATIBILITY. Разрешение на эксперимент не заменяет критерии стабильного выпуска.

## Bitrix24: явное включение чтения

Dev.3 поддерживает установленный enabled/trusted Bitrix24 0.9.0-rc.1. Добавьте `"bitrixReadOnly": true` в приватный `config.json`, сохраняя остальные поля и права 0600; затем перезапустите службу панелей. При отсутствии поля адаптер выключен, старые конфиги сохраняют поведение dev.2. Выключение флага возвращает регистрационную карточку и не изменяет настройки Bitrix24.

Адаптер использует стандартное размещение Ивы: `IVA_DATA_DIR/custom/plugins/bitrix24-read/server.mjs`, соседний `bitrix24-read.env` и `IVA_DATA_DIR/plugin-data/bitrix24-read`. Env должен быть приватным обычным файлом не больше 16 KiB. Произвольные команды, пути и tool names в конфиге не допускаются. Адаптер не запускает installer/updater. Неподдерживаемая версия, повреждённый ответ или отказ MCP показывают сообщение с кнопкой повторной проверки и возвратом.

Проверка после установки: `/panels` → Bitrix24 → Действия → Настройки Bitrix24 → Данные сотрудников → Настройки Bitrix24 → Подключение → Настройки Bitrix24 → Права webhook. Убедитесь, что редактируется одно сообщение, обычные ответы Ивы продолжаются, а приватные настройки/предложения Bitrix24 не меняются. Сначала сравните ревизию с прежним разговорным меню. Новая версия не редактирует настройки через кнопки.
