# Исследовательский запуск

Это инструкция для изолированной проверки разработчиком. Отдельный разрешённый владельцем боевой эксперимент с установкой и сменой маршрута Bridge описан в [COMPATIBILITY.md](COMPATIBILITY.md); он не заменяет проверки вашей установки.

## Предварительные условия

Node.js 24, Linux, `bash` и `flock`. Manifest описывает service plugin; `server.mjs` включает runtime зависимости. Для запуска сервису нужны `PLUGIN_ROOT`, `PLUGIN_DATA`, `IVA_DATA_DIR`, `IVA_SERVICE_PORT`, которые менеджер служб Ивы задаёт при установке. При отдельном тесте оператор задаёт их явно; адрес данных и порт берутся из изолированного окружения.

Создайте отдельный приватный каталог `PLUGIN_DATA` с правами 0700. Создайте в нём `config.json` с правами 0600:

```json
{
  "upstream": "http://127.0.0.1:9000",
  "secret": "REPLACE_WITH_BRIDGE_SECRET",
  "botToken": "123:REPLACE_WITH_TEST_BOT_TOKEN",
  "owners": [123],
  "mode": "passthrough"
}
```

Это placeholders. `upstream` должен быть исходным HTTP origin Eve, а порт сервиса должен отличаться. Реальные секреты передаются только через приватный файл. Даже режим passthrough сейчас требует полный config и доступное корректное состояние. Режим по умолчанию — passthrough; `/panels` в нём передаётся Иве.

Запускайте из каталога сервиса:

```sh
bash launch.sh
```

Проверка `GET /health` на loopback порту службы возвращает режим и факт работы HTTP listener. Она не проверяет Telegram, Eve, очередь или доступность внешних интеграций. Панели читают `custom/plugins.json` внутри `IVA_DATA_DIR`.

## Перед экспериментальным подключением Bridge

Проверьте exact SHA ядра и поведение Bridge по [COMPATIBILITY](COMPATIBILITY.md). Сохраните прежнюю конфигурацию маршрута и способ её восстановления. В отдельном тестовом окружении сначала проверьте passthrough, затем явно включите `mode: panels`. Только адрес назначения Bridge (`ASSISTANT_HOST` в исследованной версии) направляется на loopback порт iva-panels; origin настоящего Eve остаётся прежним и указан в config.

Порт 8735 в descriptor является запрашиваемым; используйте реально назначенный `IVA_SERVICE_PORT`, а не предполагайте свободный фиксированный порт. Никогда не направляйте upstream на сам сервис. При возврате Bridge на исходный адрес сначала проверьте прямую связь с Eve, затем остановите iva-panels. Никакое изменение маршрута не выполняется автоматически плагином.

Обязательный smoke: обычный текст, native menu, reset/cancel, открытие `/panels`, переходы в одном сообщении, дубликат и stale button, restart, очередь при занятом агенте, удалённое сообщение, отказ Telegram и возврат исходного маршрута. Изолированный маршрут модулей Bridge и собранного сервиса проверяется автоматически. В боевом эксперименте подтверждены обычный ответ Ивы, ручная навигация, restart и возврат исходного маршрута. Busy queue, отказы Telegram, native menu и reset/cancel остаются автоматическими проверками; полную матрицу живых сценариев ещё предстоит пройти.

## Диагностика

Ошибка запуска сообщает только общий код ситуации: проверьте переменные среды, права config, loopback upstream, разные порты и валидность state. Секреты и URL Bot API в журналы не выводятся. Не обходите ошибку состояния автоматическим удалением `screens.json`; сохраните приватную копию и исследуйте причину. Неоднозначную отправку заменяют новым `/panels`, а не повторной доставкой того же события.

## Штатная установка службы в Iva 0.4.12

После подготовки приватной конфигурации и явного разрешения владельца экспериментальная служба ставится штатным путём предложения плагина:

```sh
iva plugin propose /path/to/iva-panels/plugin
```

Владелец получает в своём Telegram-чате Ивы сообщение «Плагин iva-panels просит установку» и нажимает «Установить». После этого Bridge ставит точную копию предложения с проверкой digest. Прямой неинтерактивный `plugin add --trust` для `sh.iva/` штатный установщик отклоняет; подтверждение не подменяют искусственным callback или редактированием реестра.

Служба должна сначала ответить на HTTP probe, а не только показать active в systemd. Дождитесь listener и подтвердите проход health-запроса до исходного Eve, прежде чем менять маршрут Bridge. Для временного маршрута используйте отдельный override только службы Bridge; общий environment Eve остаётся прежним. Сохраните baseline, подготовьте route-only rollback и не восстанавливайте живые queue/offset/policy целиком из резервного снимка. Обратное подключение тоже ждёт готового listener.

Результаты первого разрешённого боевого эксперимента и оставшиеся проверки — в COMPATIBILITY. Разрешение на эксперимент не заменяет критерии стабильного выпуска.

## Bitrix24: явное включение чтения

Dev.3 поддерживает установленный enabled/trusted Bitrix24 0.9.0-rc.1. Добавьте `"bitrixReadOnly": true` в приватный `config.json`, сохраняя остальные поля и права 0600; затем перезапустите службу панелей. При отсутствии поля адаптер выключен, старые конфиги сохраняют поведение dev.2. Выключение флага возвращает регистрационную карточку и не изменяет настройки Bitrix24.

Адаптер использует стандартное размещение Ивы: `IVA_DATA_DIR/custom/plugins/bitrix24-read/server.mjs`, соседний `bitrix24-read.env` и `IVA_DATA_DIR/plugin-data/bitrix24-read`. Env должен быть приватным обычным файлом не больше 16 KiB. Произвольные команды, пути и tool names в конфиге не допускаются. Адаптер не запускает installer/updater. Неподдерживаемая версия, повреждённый ответ или отказ MCP показывают сообщение с кнопкой повторной проверки и возвратом.

Проверка после установки: `/panels` → Bitrix24 → Действия → Настройки Bitrix24 → Данные → Настройки Bitrix24 → Подключение → Настройки Bitrix24 → Права webhook. Убедитесь, что редактируется одно сообщение, обычные ответы Ивы продолжаются, а приватные настройки/предложения Bitrix24 не меняются. Сначала сравните ревизию с прежним разговорным меню. Новая версия не редактирует настройки через кнопки.

## Rich-карточки

Dev.4: `"presentation": "rich"` включает `sendRichMessage` с HTML и block buttons; редактирование остаётся через `editMessageText` с rich_message. `classic` сохраняет прежнюю inline-клавиатуру. Выбор независим от глобального вида меню Ивы и требует рестарта службы панелей. Перед сменой проверьте отсутствие pending доставки; затем откройте новый `/panels`. В режиме rich устаревшая inline-клавиатура убирается при редактировании. Неизвестная отправка не переключается автоматически на другой метод: это могло бы создать дубликат. При несовместимом клиенте верните `classic` и откройте новую панель. Формат state не менялся: styles вычисляются только при доставке, но новый config presentation перед downgrade нужно удалить.

## Редактор Bitrix24

Dev.5: отдельно включите `"bitrixSettings": true` при `bitrixReadOnly=true`. Панели сохраняют настройки через существующий Bitrix24 0.9.0-rc.1; задачи и документы не меняют. Перед обновлением сохраните приватный config и код, проверьте отсутствие pending действий/доставки. После установки откройте новый `/panels`, выберите другой режим и сначала проверьте preview → «Отменить». Подтверждать изменение следует только при реальном желании поменять настройки. Проверьте выбор полей сотрудников, email, устаревшую кнопку и обычный ответ Ивы.

Для выключения редактора уберите флаг или задайте false и перезапустите службу. Старый preview уже не применится через панели. Его offer живёт до срока Bitrix или отмены через прежнее меню; выключение редактора не восстанавливает политику. Для downgrade до dev.4 удалите новый config field; сначала убедитесь, что все `acting` квитанции завершены чтением результата через текущую версию. Старый код не понимает фазу acting, не сбрасывайте screens.json для обхода этой проверки. Уже сохранённые настройки остаются актуальными и не восстанавливаются из резервов автоматически.

## Панель отправки файлов

Dev.6 не требует нового config flag. Для включённого и доверенного `file-delivery` открывается отдельная карточка; version читается из установленного manifest. Открытие карточки/правил/раздела обновлений не обращается к GitHub. Только явная «Проверить stable» требует исходящий HTTPS к api.github.com и raw.githubusercontent.com; токен GitHub не нужен. До установки/обновления самого файлового плагина дело не доходит. Для штатного предложения используйте разговорный updater Ивы.

После установки откройте свежий `/panels` → Отправка файлов → Правила отправки → Отправка файлов → Обновления → Проверить stable → Отправка файлов → К плагинам. Все переходы должны менять одно сообщение. Проверьте версию и результат GitHub, затем обычный ответ Ивы. Формат screens/config не менялся относительно dev.5; downgrade до dev.5 выполняется возвратом source и штатным update без восстановления живого state/settings. Сохранённые новые files-кнопки старой версии не поддерживаются: откройте свежий `/panels`.

## Общий каталог и страницы плагинов

Dev.7 не требует нового config. Новый /panels показывает все регистрации, включая сам Panels; выключенные и без доверия получают базовые карточки. При длинном списке используйте Далее/Назад. Поддержка новых страниц — panels.json в устанавливаемом корне плагина, [контракт v1](PLUGIN_API.md). Дополнительный install/trust через Panels не выполняется.

После обновления проверьте весь список и новую базовую карточку, затем прежние меню Битрикса и файлов. Новые generic/card/page IDs не поддерживаются dev.6: при возврате старого кода откройте новый /panels. Формат state/config/acting сохранён. Не восстанавливайте живые screens/settings/queue из резервов.

## Управление состоянием плагинов

Dev.8: по умолчанию этих кнопок нет. Оператор может добавить в приватный config:

```json
{ "lifecycle": { "cli": "/opt/iva/current/bin/iva.mjs" } }
```

Это пример пути, замените его фактическим абсолютным путём к штатному CLI. Используйте ссылку current: после сборки она должна указывать на новую версию. Конфиг остаётся 0600. Нужны Linux, Node 24, пользовательская сессия systemd с XDG_RUNTIME_DIR и права того же пользователя, который управляет Ивой. Оператор доверяет Panels право выполнять только `plugin enable NAME` и `plugin disable NAME` через этот CLI; установка, обновление, удаление и выдача доверия сюда не входят. Перезапустите только службу Panels, затем откройте новый `/panels`.

Сначала проверьте карточку → Управление плагином → Выключить плагин → Отменить. Подтверждайте только нужное вам изменение. После подтверждения кратковременно может пропасть ответ Ивы: штатный менеджер пересобирает MCP/code плагины и переключает версию. Панели и единственный Bridge продолжают работать своими службами. Проверяйте результат кнопкой; если старый экран истёк, откройте новый и выберите Последняя задача. Проверка результата не выполняет команду повторно.

Задача запускается в единственной пользовательской unit `iva-panels-lifecycle.service`, Restart=no, RuntimeMaxSec=900. CLI имеет собственный предел 600 секунд; дочерние процессы остаются в cgroup задачи. Preview/queued/running/result хранятся в приватном `lifecycle/<UUID>.json` (0600). queued/running блокируют новые команды глобально. После аварии они не снимаются автоматически: оператор проверяет unit, реестр, текущую версию, службы и health, сохраняет журнал и только затем фиксирует выясненный исход. Не запускайте worker вручную параллельно, не удаляйте pending jobs для обхода защиты. При более чем 100 сохранённых задачах нужна архивная уборка оператором только завершённых/неотправленных задач; незавершённые не удалять.

Для отключения функции уберите `lifecycle` и перезапустите Panels. Это не отменяет уже переданную отдельную задачу и не включает выключенный плагин обратно. Для возврата dev.7 сначала исключите queued/running/acting; удалите новый config field, верните прежний source и выполните штатный update Panels. Состояние других плагинов, screens, очереди и настройки из резервов не восстанавливаются. Старые life-кнопки не поддерживаются dev.7: откройте свежую панель. Если вернуть исходный маршрут Bridge, текущая задача тоже продолжит работу до завершения или предела; её исход проверяется отдельно.

При native disable реестр может уже показывать enabled=false, пока старая Ива ещё работает с extension. Дождитесь terminal результата через «Проверить результат»; не используйте только флаг карточки как доказательство завершения. Core `send_file` остаётся независимым способом отправки, enable/disable file-delivery им не управляет.
