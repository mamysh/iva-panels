# Общий API настроек и действий

Контракт iva-panels/v2 добавлен в 0.2.0-dev.1. Он необязателен для плагина и не требует изменений ядра. V1 и встроенные адаптеры сохранены для совместимости. Включение/выключение использует штатный lifecycle независимо от этого API. API описывает доступные экраны и конечный набор действий; Panels не читает произвольные config/env и не выбирает shell или MCP endpoint.

## Поставка и транспорт

Установленный плагин кладёт рядом с plugin.json:

```json
{
  "schema": "iva-panels/v2",
  "plugin": "notes",
  "pluginVersion": "1.0.0",
  "entry": "home",
  "capabilities": ["settings"]
}
```

`plugin` и `pluginVersion` совпадают с manifest. `capabilities` содержит settings и/или actions, без повторов. Это объявление возможностей, не разрешение записи. Лишние поля, команды, адреса и пути отвергаются. [Schema](panels-v2.schema.json), проверка: `node scripts/check-panel.ts /path/to/plugin`.

Плагин обслуживает HTTP POST `/panels/v1` через Unix socket **PLUGIN_DATA/panels.sock** (0600, владелец — пользователь Ивы). Panels вычисляет путь из имени регистрации: `IVA_DATA_DIR/plugin-data/<name>/panels.sock`. Каталог должен иметь канонический путь без symlink; конечный объект — настоящий socket. Секреты остаются внутри плагина. Нет второго MCP клиента, захвата сессии, второго getUpdates и публичного порта API. Один запрос ограничен 5 секундами, ответ — 32 КиБ, redirects не используются.

Оператор разрешает общий API параметром `"dynamicPanels": true` в приватном конфиге Panels. По умолчанию false. Это доверие ко всем включённым и trusted плагинам с корректным v2, а не отдельная авторизация каждого бизнес-действия. Недоверенный или выключенный плагин никогда не вызывается. Socket не изолирует процессы одного Unix-пользователя друг от друга: это прежняя граница доверия установленным плагинам.

Плагин может добавить socket в собственный работающий сервис или отдельный `sh.iva/services/panels`. Для отдельной службы нужен manifest `extensions.sh.iva`, service.json и свободный служебный порт по правилам Ивы, даже если она обслуживает только socket. При выключении службы останавливает Ива. Без Panels плагин продолжает работать, использует прежние настройки и свои инструменты.

## Запросы и ответы

Каждый запрос содержит `schema: "iva-panels/rpc-v1"`, `plugin`, `pluginVersion` и поля операции. Плагин проверяет личность и версию, отклоняет неизвестные операции/поля. Ответ HTTP 200:

```json
{
  "schema": "iva-panels/rpc-v1",
  "plugin": "notes",
  "pluginVersion": "1.0.0",
  "result": {
    "state": "screen",
    "revision": 0,
    "title": "Настройки заметок",
    "body": "Компактный вид: выключен",
    "rows": [[{ "label": "Включить компактный вид", "action": "compact-on" }]]
  }
}
```

| Операция | Поля запроса сверх общего envelope | result                                              |
| -------- | ---------------------------------- | --------------------------------------------------- |
| read     | page                               | screen: revision, title, body, rows                 |
| prepare  | action, revision, token            | offer: token, revision, expiresAt, summary          |
| confirm  | token                              | done: token, revision, message                      |
| cancel   | token                              | cancelled: token, revision, message                 |
| status   | token                              | сохранённый done/cancelled либо незавершённый offer |

`revision` — целое 0…999999999999. ID страницы и действия — `[a-z][a-z0-9-]{0,23}`. `token` — 24 hex символа; его генерирует Panels **до prepare**. При prepare плагин может вернуть `{"state":"rejected","token":"<тот же token>","message":"Причина и следующий шаг"}`: это подтверждает, что предложение с этим token не создано и эффект не выполнен. Например, revision устарела или другой интерфейс занял предложение. Только такой проверенный ответ снимает preparing без uncertain; потерянный ответ или ошибка записи остаются неизвестным исходом.

Плагин сохраняет этот token с предложением, а затем с терминальной квитанцией. Status только читает. Он никогда не подтверждает/отменяет, не повторяет запрос и не создаёт эффект.

Screen: title до 80, body до 1500, до пяти рядов по одной/две кнопки. Кнопка содержит ровно label (1…48) и `target` (переход) либо `action` (prepare). Actions уникальны в пределах плагина и не требуют page в prepare. Текст буквальный, с HTML escaping; размер итогового сообщения проверяется отдельно. Нельзя задавать callback IDs, пути, URLs, tools, command, стили или произвольные аргументы. Panels добавляет обновление и выход. Ответ read с action должен быть чистым чтением.

Offer: summary — полное описание текущего и нового состояния, последствий и нужных прав, 1…1500 символов; expiresAt — Unix миллисекунды в будущем, не дальше 15 минут. Offer возвращает исходные token/revision. Prepare сохраняет только предложение, **не меняет настройки и не выполняет действие**. Значения из внешних данных не являются полномочиями, подтверждение принадлежит владельцу через сохранённый экран Panels.

Confirm проверяет token, TTL, текущую revision, права и бизнес-валидацию. Успешный результат увеличивает revision ровно на один; cancel возвращает исходную revision и не меняет рабочие настройки. Повтор confirm/cancel того же token возвращает сохранённую квитанцию, без нового эффекта. Settings, revision и квитанция должны фиксироваться атомарно. Для внешнего действия нужна собственная идемпотентность и восстановление плагина: пример ниже решает только локальные настройки.

## Восстановление

Panels сохраняет preparing до prepare, offered после проверки ответа, confirming/cancelling до эффекта, done/cancelled после ответа. Все записи приватные, атомарные с fsync. На плагин хранится одна актуальная задача. Новый выбор не заменяет активное предложение в другом экране. Просроченное предложение можно заменить; плагин тоже проверяет TTL.

Подтверждение связано с полным снимком регистрации и descriptor. Изменение версии, SHA, digest, доверия, включённости или descriptor не позволяет выполнить старое предложение. Ручные внешние изменения плагин обязан учитывать своей revision; Panels не предоставляет CAS с другими администраторами.

После потерянного ответа или аварии запись остаётся pending/uncertain. Panels не повторяет prepare/confirm/cancel; новое действие блокируется. «Проверить результат» вызывает status и принимает только терминальную квитанцию с тем же token и ожидаемой revision. Если status ещё показывает offer, разблокировать нужно через собственный путь отмены/проверки плагина и затем status. При смене личности/версии нужна операторская сверка; автоматического сброса журнала нет. Не удаляйте pending journal ради повторного запроса.

Экран привязан к owner/chat/message/revision/TTL штатным Engine. Сервер плагина получает token, но не Telegram credentials. Внешний плагин обязан сохранить свои права и обычный путь настройки. Bridge остаётся доверенной локальной границей; отдельной криптографической аттестации ручного нажатия нет.

## Пример для разработчика и Ивы

[dynamic-notes](../examples/dynamic-notes/) — полный синтетический пакет с service, descriptor и зависимостью только на Node 24. Порт в примере следует заменить на свободный по правилам установки. Он сохраняет одну локальную настройку вместе с revision и receipt, возвращает результат после атомарной записи и поднимает socket после рестарта. Это пример, а не встроенный адаптер Panels.

Необязательный [settings-service.mjs](../plugin/skills/iva-panels-integration/resources/settings-service.mjs) поставляется с plugin skill и может быть скопирован в свой плагин. Его функции validate/screen/propose определяются автором. Он подходит для плагина, которому этот файл служит единственным источником локальных настроек. Для существующего storage нужен адаптер к его текущему авторитетному хранилищу: нельзя создать вторую несогласованную конфигурацию. Внешние бизнес-записи helper не выполняет.

[Поставляемый skill](../plugin/skills/iva-panels-integration/SKILL.md) объясняет Иве подключение существующего и проектирование нового плагина. Skill загружается стандартным механизмом Ивы после установки Panels. Это инструкция по запросу, а не автоматический патч чужих исходников и не глобальный перехват генератора плагинов. Карточка «Подключить к Panels» содержит готовый запрос для загрузки skill. Для независимого автора доступны этот контракт, schema и пример.

## Проверено в разработке

Реальный socket и helper, discovery, read/prepare/cancel/confirm/status, повтор confirm после перезапуска клиента, потерянный ответ, блокировка pending, чужой владелец, stale кнопка, delivery retry без второго эффекта, смена registry/версии, TTL, ошибочные права socket, symlink и несовместимые ответы проверяются в `test/dynamic.test.ts`. Проверка descriptor не доказывает доступность службы. Карточка поэтому отличает «API объявлен» от фактического ответа при открытии. Linux CI прошёл 82 теста и три stock Bridge версии; exact 2afd9e4 установлен штатным обновлением Panels. Ручной Telegram smoke ожидается, настоящие Bitrix/files пока не переведены на v2. Подробности — [COMPATIBILITY](COMPATIBILITY.md).
