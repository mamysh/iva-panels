# Карточки действий в чате

Доступно в **0.3 RC** поверх [v2 API плагина](CONTRACT.md).
Плагин может показать готовое предложение прямо в личном чате Ивы,
без перехода через каталог. Panels не получает бизнес-логику операции.

## Требования

- У Panels `mode: panels`, `dynamicPanels: true` и ровно один настроенный owner.
- Плагин включён, доверен, имеет корректный v2 descriptor и работающий `panels.sock`.
- Оба процесса работают в доверенном локальном окружении пользователя Ивы.
- Socket Panels — `IVA_DATA_DIR/plugin-data/iva-panels/chat.sock`, режим 0600.

Это локальный API, не публичный HTTP endpoint и не граница изоляции процессов
одного Unix-пользователя. Свободный ввод текста или ответ модели не заменяет
callback сохранённой карточки; доверие к локальному Bridge сохраняется.

## Запрос

HTTP POST `/cards/v1` через Unix socket:

```json
{
  "schema": "iva-panels/chat-v1",
  "plugin": "dynamic-notes-example",
  "action": "toggle-compact",
  "revision": 0,
  "requestId": "0123456789abcdef01234567"
}
```

`revision` — актуальная revision плагина. `requestId` — 24 строчных hex символа,
созданные один раз для конкретного предложения и сохранённые плагином до запроса.
Повтор использует тот же ID. Нельзя создавать новый ID для обхода неизвестной доставки.
Имя `plugin` проходит ту же схему, что каталог Ивы: до 64 строчных латинских
букв/цифр, допустимы внутренние `-` и `.`, запрещены `--`, `..` и разделитель
в начале/конце. `action` соответствует v2 правилу `[a-z][a-z0-9-]{0,23}`.
Оба значения должны соответствовать зарегистрированному плагину и его API.

Пример для изолированного synthetic-notes окружения, где `IVA_DATA_DIR` уже задан:

```sh
curl --unix-socket "$IVA_DATA_DIR/plugin-data/iva-panels/chat.sock" \
  --header 'Content-Type: application/json' \
  --data '{"schema":"iva-panels/chat-v1","plugin":"dynamic-notes-example","action":"toggle-compact","revision":0,"requestId":"0123456789abcdef01234567"}' \
  http://localhost/cards/v1
```

В рабочем плагине используйте HTTP client с deadline и ограничением ответа.
Не передавайте owner/chat ID, адрес Telegram, callback ID, shell или `confirm`:
лишние поля отвергаются. Получателя и кнопки создаёт Panels.

## Ответ

HTTP 200:

```json
{ "schema": "iva-panels/chat-v1", "state": "presented" }
```

| State               | Что известно                                                                             |
| ------------------- | ---------------------------------------------------------------------------------------- |
| `presented`         | Ответ Telegram с message ID получен и сохранён.                                          |
| `already_presented` | Карточка с таким ключом уже отправлена; второго сообщения нет.                           |
| `delivery_unknown`  | Результат prepare/send или сохранения доставки не доказан; повторная отправка запрещена. |

Это **статус доставки**, не подтверждение действия и не успешная бизнес-операция.
HTTP 400 с `{"error":"CHAT_CARD_UNAVAILABLE"}` означает общий отказ проверки
или обработки. Не считайте его доказательством отсутствия эффекта prepare/send:
ошибка могла произойти после сохранения намерения. Если HTTP-ответ потерян,
повторяйте только тот же запрос; не создавайте новый requestId автоматически.

## Порядок обработки

1. Panels проверяет вход и единственный owner, вычисляет ключ из plugin/action/revision/requestId.
2. Сохраняет delivery intent до обращения к плагину и Telegram.
3. Вызывает только v2 **prepare**. Плагин проверяет данные и возвращает предложение без эффекта.
4. Отправляет карточку от текущего бота, сохраняет message ID и привязку кнопок.
5. Callback владельца запускает прежний v2 confirm/cancel; status остаётся чтением результата.

Проверяются пользователь, личный чат, сообщение, revision и срок экрана.
Отмена и подтверждение принадлежат бизнес-контракту плагина. Терминальное сообщение
об успехе должно опираться на его результат, а не на `presented`.

## Сроки, повторы и пределы

Экран живёт до 15 минут; предложение плагина может истечь раньше.
Повтор закрытой, истёкшей или принадлежащей другому owner карточки отвергается.
Delivery intent и неизвестная отправка сохраняются после рестарта.

До 100 экранов в store. API карточек сам их не очищает: при заполнении новые
карточки отклоняются. Обычное событие `/panels` очищает истёкшие экраны, у которых
нет защищённых acting/editing событий. Такая очистка не является вечным журналом
requestId: защиту бизнес-операции от повторов обязан обеспечивать плагин.
Не удаляйте state или pending журналы, чтобы повторно отправить карточку.
